# Plan: assign a vendor and let the vendor work on their own tasks

## Research findings

**Database**
- `profiles_role_check` is `('manager','admin')` and the default is `manager`. The role-change order is in `conventions.md`: drop the check, update data, set the default, add the new check.
- `launch_run` is last defined in `20261026084454_template_versions.sql` §7.
  - The caller must be `manager` or `admin`, so a vendor already gets `NOT_ALLOWED`.
  - The `INVALID_ASSIGNEE` check rejects any assignee outside `manager`/`admin`. Vendors must be added to that list.
  - Tasks without an assignment already go to the launching user. Assignment keys are `version_tasks.id`.
- `mark_task_done` allows the admin, the assignee or the run manager. A vendor is never the run manager, so a vendor marking someone else's task already gets `NOT_ALLOWED`.
  - `run_tasks` and `runs` grant only `select` to `authenticated`, so direct updates and inserts are already denied. Grants must not be widened.
- **Leaks that appear once a vendor exists** (these need real changes):
  - `run_tasks_select_visible` uses `can_see_run(run_id)`. A vendor who has one task in a run would see all tasks of that run, which breaks AC-VENDOR-04.
  - `templates_select_admin_or_published` is open to anyone when `current_version_id is not null`.
  - `template_versions_select`, `version_sections_select` and `version_tasks_select` allow `is_current_version(...)` and `is_version_of_visible_run(...)`. Both are true for a vendor, which breaks AC-VENDOR-08.
  - `template_sections` and `template_tasks` are admin-only already.
- `list_assignable_users` returns `id, email`, filters on `role in ('manager','admin')` and requires the caller to be a manager or admin. Vendors must be added to the returned set. Vendor callers keep getting nothing. `profiles` RLS already hides other users' emails from a vendor.
- `can_see_run` already lets a vendor see runs where they are an assignee, so the `runs` policy needs no change (AC-VENDOR-03, AC-VENDOR-06, AC-VENDOR-10).

**Application**
- `Role` in `src/lib/templates/domain.ts` is `manager | admin`.
- `tests/vendor/contract.ts` fixes the pure functions the tests expect:
  - In `runs/domain`: `yourTasksLabel`, `vendorRunListRows`, `vendorRunView`, `vendorRunsListView`. The tests assume the strings `Your tasks: N of K done`, `Run not found`, `required`/`optional`, `to do` and `in progress`.
  - In `templates/domain`: `templatesListAccess(role)`, with `{kind:"denied", message:"Not enough rights"}` for a vendor.
- Pages to adapt:
  - `src/app/runs/page.tsx` and `src/app/runs/[id]/page.tsx`
  - `src/app/runs/new/page.tsx` and `src/app/templates/**`
  - `app-nav.ts`
  - `src/app/runs/actions.ts`
- The runs list embeds `run_tasks(status)`, and the run page loads its tasks the same way. With the stricter RLS, both queries return only the vendor's own tasks, so the pure functions work on the RLS-filtered data.

## Design

One new migration, dated after `20261027105115`, for example `20261109120000_vendor_role.sql`. It has no new tables and no new grants.
1. Role set, in the convention's order: drop the check, set the default to `manager`, add the check `('manager','admin','vendor')`.
2. Redefine `private.launch_run`: copy the current body and change only the assignee check to `role in ('manager','admin','vendor')`.
3. Recreate `list_assignable_users` (same `id, email` columns) so it includes vendors. Callers must still be a manager or admin.
4. Replace the policies, one per operation, `to authenticated`, `(select ...)` style.
   - `run_tasks_select_visible`: `(role = 'vendor' and assignee_id = (select auth.uid())) or (role is distinct from 'vendor' and private.can_see_run(run_id))`.
   - `templates_select_admin_or_published`: add `role in ('manager','admin')` to the published branch.
   - `template_versions_select`, `version_sections_select` and `version_tasks_select`: the `is_current_version` and `is_version_of_visible_run` branches apply only to non-vendors.
5. Leave `mark_task_done` as it is. Add a comment that its existing rule already means "a vendor marks only their own task". Redefine it only if the tests show a gap.

Application changes:
- Add `vendor` to `Role`.
- Add the pure functions from the contract.
- Add `templatesListAccess`.
- Gate the pages:
  - Vendor on `/templates`, `/templates/[id]` and `/runs/new`: `Not enough rights`, with no template data fetched.
  - Vendor on `/runs`: the vendor list, with `Your tasks: N of K done`. An empty list shows `No tasks assigned to you yet.` and no table.
  - Vendor on `/runs/[id]`: only their own tasks, with no emails, no whole-run progress and no run manager line. `Mark as done` appears on their tasks.
  - Vendor nav shows only `Runs`.
- The launch form's assignee picker already uses `list_assignable_users`, so vendors appear there once the database change is in.

## Risks

- **Confirmation for the last required task.** `markTaskDone` asks for confirmation when the task is the last required one, based on the tasks the caller can see. A vendor sees only their own tasks, so their last required task would look like the run's last one and trigger a false confirmation. For vendors, skip the pre-check and let the database decide. Run completion is already handled in `mark_task_done`.
- **Policy gaps are silent.** A missed `is_version_of_visible_run` branch leaks template tasks to a vendor without failing a visible test. Hidden scenarios may probe it, so test every `version_*` table and `templates` as the vendor.
- **Policy rewrites and existing tests.** Rewriting the `run_tasks` and template policies can break `AC-TASK-06` and `AC-EDITOR-02` for managers. Run the full suite after slice 2.
- **Redefining `launch_run`.** `create or replace` must keep the `AC-EDITOR-06` body (version snapshot, case-name trim) and change only the assignee role list.
- **`list_assignable_users` changes.** Hiding the existing `manager`/`admin` rows from vendor callers must not break `AC-RUN-10`. Keep the columns `id, email`, because `vendor-02` asserts exactly those keys.
- **Spec questions.** The reading log mentions open questions Q1–Q3 for slice 3, in issues #41, #44 and #47. I did not open them. Check them before slices 4–5, because they may affect wording or the rules for vendors.
- **Environment limits.** Tests run only through `node scripts/factory-tap.mjs` and `node node_modules/vitest/vitest.mjs run`. The factory's own checks decide acceptance.
